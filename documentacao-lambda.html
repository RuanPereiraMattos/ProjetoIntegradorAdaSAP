🎯 Problema

Empresas de médio porte perdem receita por não identificar clientes em risco de churn a tempo e por não ter visibilidade consolidada do pipeline. Gestores tomam decisões com dados dispersos em planilhas, sem alertas automáticos — resultando em oportunidades perdidas, follow-ups esquecidos e cancelamentos evitáveis.

Dados de satisfação (NPS) separados das transações de venda — não consegue correlacionar queda de NPS com risco de churn.
📋 User Stories
US-01 Visão do pipeline em tempo real
Como Gerente Comercial, quero visualizar o funil de vendas com taxas de conversão por etapa, para identificar gargalos antes de perder negócios no mês.
Dashboard exibe contagem e valor total por etapa (prospecção → proposta → negociação → fechado)
Taxa de conversão entre etapas calculada automaticamente
Etapas com conversão abaixo de 30% exibem alerta visual
US-02 Alerta de clientes em risco de churn
Como Analista de CX, quero receber automaticamente clientes sem compra há ≥ 90 dias com o ticket médio histórico, para priorizar ações de reativação.
Lista atualiza diariamente com clientes inativos há ≥ 90 dias
Cada item exibe: nome, dias sem compra, ticket médio e ação sugerida
Ticket médio > R$3.000 recebe ação diferenciada (desconto 10%)
US-03 Alerta de NPS crítico
Como Analista de CX, quero ser notificado quando um cliente registrar 3+ avaliações consecutivas ≤ 6, para acionar Customer Success antes que o cliente se torne detrator.
Sistema avalia últimas 3 avaliações de cada cliente após cada nova resposta
Cliente aparece no painel de alertas com status "NPS Crítico"
Alerta inclui as notas recentes e botão de acionamento do CS

⚡ Handler Lambda — Exemplo: fn-insights (churn-risk)

Cada função Lambda recebe o evento do API Gateway, executa a lógica de negócio e retorna um objeto com statusCode e body. Não há servidor Express — o API Gateway monta o contexto HTTP.

// fn-insights/churn-risk.mjs — Node.js 20.x import * as repo from './repository.mjs'; export const handler = async (event) => { const dias = event.queryStringParameters?.dias ?? 90; const clientes = await repo.getClientesSemPedido(dias); return { statusCode: 200, headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ total: clientes.length, clientes }), }; };

🧠 Regras de Insight (Pseudocódigo)
I-01 — Risco de Churn
FUNÇÃO calcularChurnRisk(diasLimite = 90): PARA CADA cliente: diasSemCompra = diasDesde(ultimoPedido) SE diasSemCompra >= diasLimite: SE ticketMedio > 3000: acao = "Oferta 10% desconto" SENÃO: acao = "Ligar para relacionamento" RETORNAR lista ordenada por ticketMedio DESC
I-02 — NPS Crítico
FUNÇÃO alertasNPS(): PARA CADA cliente: avaliacoes = buscar(limite=3, ordem="DESC") SE avaliacoes.length == 3: SE TODAS nota <= 6: ADICIONAR alerta: acao = "Acionar CS imediatamente" RETORNAR resultado
I-03 — Gargalo no Funil
FUNÇÃO analisarFunil(): etapas = ["prospeccao", "proposta", "negociacao", "fechado_ganho"] PARA CADA par de etapas consecutivas: taxa = total_proxima / total_atual SE taxa < 0.30: ADICIONAR alerta { de, para, taxa, mensagem: "Gargalo detectado" } RETORNAR alertas ← atualmente: Proposta→Negociação em 22%

🔄 Fluxo de Requisição — GET /insights/churn-risk (Serverless)
1
Gerente abre o Dashboard no React
2
React dispara GET /insights/churn-risk?dias=90 com header Authorization: Bearer <JWT> para o API Gateway
3
API Gateway aciona o Lambda Authorizer (fn-auth) para validar o JWT antes de qualquer processamento
4
fn-auth valida a assinatura do token e retorna uma IAM Policy permitindo ou negando a chamada
5
API Gateway roteia para fn-insights com o contexto do usuário (role, id) já injetado no evento
6
fn-insights conecta ao RDS via RDS Proxy (reutiliza conexão do pool) e executa a query de churn risk
7
Função retorna { statusCode: 200, body: JSON.stringify(resultado) } — API Gateway converte para resposta HTTP
8
React renderiza os cards de alerta no Dashboard com botão "Acionar"

⚡ Lambda vs Elastic Beanstalk — Comparativo
Critério⚡ Lambda (esta versão)🖥️ Elastic Beanstalk
Custo em idle $0 — escala para zero automaticamente ~$5–10/mês (EC2 rodando mesmo sem requisições)
Gerenciamento de servidor Nenhum — AWS gerencia tudo Patching do SO, monitoramento de instância
Escala horizontal Automática e ilimitada (cada invocação é isolada) Auto-scaling com warmup (minutos para subir instância)
Deploy independente fn-insights pode ser atualizada sem afetar fn-clientes Deploy substitui a aplicação inteira no EC2
Cold start 50–200ms em Node.js (primeira invocação após idle) Sem cold start — servidor sempre quente
Limite de execução Máximo 15 minutos por invocação Sem limite de duração
Connection pooling com RDS Exige RDS Proxy (custo adicional ~$10–15/mês) Pool gerenciado pela própria aplicação Express
