Transação → Regra de Negócio → Insight → Ação
Módulo do ERP corporativo com dois pilares: clientes em risco de churn (inatividade + NPS) e funil de vendas (oportunidades por etapa). API Node.js + Express hospedada no Elastic Beanstalk — sem login próprio. O Express middleware valida o JWT emitido pelo ERP e injeta { userId, role } em cada requisição.

Problema · Personas · User Stories · MVP · Insights
🎯 Problema

Empresas de médio porte perdem receita por não identificar clientes em risco de churn a tempo e por não ter visibilidade consolidada do pipeline. Gestores tomam decisões com dados dispersos em planilhas, sem alertas automáticos — resultando em oportunidades perdidas, follow-ups esquecidos e cancelamentos evitáveis.

📊

💼

📋 User Stories
US-01 Visão do pipeline em tempo real
Como Gerente Comercial, quero visualizar o funil de vendas com proporção de estoque por etapa, para identificar gargalos antes de perder negócios no mês.
Dashboard exibe contagem e valor total por etapa (prospecção → proposta → negociação → fechado)
Proporção de estoque entre etapas calculada automaticamente
Etapas com proporção abaixo de 30% exibem alerta visual
US-02 Alerta de clientes em risco de churn
Como Analista de CX, quero receber automaticamente clientes sem compra há ≥ 90 dias com o ticket médio histórico, para priorizar ações de reativação.
Lista atualiza diariamente via batch sync com o ERP (defasagem máx. 24h)
Cada item exibe: nome, dias sem compra, ticket médio e ação sugerida
Ticket médio > R$3.000 recebe ação diferenciada (desconto 10%)
US-03 Alerta de NPS crítico
Como Analista de CX, quero ser notificado quando um cliente registrar 3+ avaliações consecutivas ≤ 6, para acionar Customer Success antes que o cliente se torne detrator.
Sistema avalia últimas 3 avaliações de cada cliente após cada nova resposta
Cliente aparece no painel de alertas com status "NPS Crítico"
Alerta inclui as notas recentes e botão de acionamento do CS

🔐 Autenticação — Token ERP via Express Middleware
// O usuário já está autenticado no ERP corporativo. // O frontend repassa o token JWT do ERP em cada requisição. // NexusVendas não tem endpoint /auth/login. GET /insights/churn-risk Authorization: Bearer <token-emitido-pelo-erp> // Express middleware (authMiddleware) em todas as rotas: // 1. Lê header Authorization: Bearer <JWT> // 2. Verifica assinatura com chave pública do IdP corporativo // 3. Verifica expiração (exp) // 4. Extrai role das claims → injeta em req.user // Token inválido → 401 Unauthorized // Token válido → req.user = { userId, role } disponível no controller
admin — acesso total gerente — leitura + insights vendedor — próprios pedidos
roles lidas das claims do token ERP
🟢 Route Handler Express — Exemplo: InsightController (churn-risk)

O Express recebe a requisição HTTP, o middleware auth valida o JWT, e o controller delega ao service. O servidor é persistente — não há cold start.

🧠 Regras de Insight (Pseudocódigo)
I-01 — Risco de Churn
FUNÇÃO calcularChurnRisk(diasLimite = 90): PARA CADA cliente: // ultimoPedido vem do sync diário do ERP // fallback p/ data_cadastro evita falso negativo no onboarding ref = ultimoPedido ?? data_cadastro diasSemCompra = diasDesde(ref) SE diasSemCompra >= diasLimite: SE ticketMedio > 3000: acao = "Oferta 10% desconto" SENÃO: acao = "Ligar para relacionamento" RETORNAR lista ordenada por ticketMedio DESC · dados com defasagem máx. 24h
I-02 — NPS Crítico
FUNÇÃO alertasNPS(): PARA CADA cliente: avaliacoes = buscar(limite=3, ordem="DESC") SE avaliacoes.length == 3: SE TODAS nota <= 6: ADICIONAR alerta: acao = "Acionar CS imediatamente" RETORNAR resultado
I-03 — Gargalo no Funil
FUNÇÃO analisarFunil(): etapas = ["prospeccao", "proposta", "negociacao", "fechado_ganho"] PARA CADA par de etapas consecutivas: SE total_atual > 0: proporcao = total_proxima / total_atual SE proporcao < 0.30: ADICIONAR alerta { de, para, proporcao, mensagem: "Gargalo detectado" } RETORNAR alertas ← atualmente: Proposta→Negociação em 22%

🔄 Fluxo de Requisição — GET /insights/churn-risk
1
Gerente abre o Dashboard no React
2
React dispara GET /insights/churn-risk?dias=90 com header Authorization: Bearer <JWT> para o servidor Express no Elastic Beanstalk
3
Express executa o middleware de autenticação → verifica assinatura JWT, extrai { userId, role } e injeta em req.user
4
Express roteia para InsightController.getChurnRisk com o contexto do usuário já disponível
5
Controller chama InsightService.getClientesSemPedido(90)
6
Service executa a regra: Repository busca clientes sem pedido via pg-pool → calcula ticket médio → monta lista com ação sugerida por faixa de ticket
7
Controller retorna res.json({ total, clientes }) — Express converte para HTTP 200 OK
8
React renderiza os cards de alerta no Dashboard com botão "Acionar"

🔒 HTTPS — TLS 1.2+ em todos os endpoints (Elastic Beanstalk)
💾 RDS encryption at rest habilitado

📋 audit_log — todo INSERT/UPDATE/DELETE rastreado pelo Service

✅ Validação — campos obrigatórios validados no Controller antes do Service

🚀 Elastic Beanstalk vs Lambda — Comparativo
Critério🚀 Elastic Beanstalk (esta versão)⚡ Lambda (serverless)
Custo em idle ~$5–10/mês (EC2 rodando mesmo sem requisições) $0 — escala para zero automaticamente
Gerenciamento de servidor Patching do SO gerenciado pelo Beanstalk (mas existe) Zero — AWS gerencia tudo
Escala horizontal Auto-scaling com warmup (minutos para subir instância) Automática e ilimitada por invocação
Deploy Deploy substitui a aplicação inteira no EC2 Cada função pode ser atualizada independentemente
Cold start Sem cold start — servidor sempre quente 50–200ms em Node.js (primeira invocação após idle)
Limite de execução Sem limite de duração por requisição Máximo 15 minutos por invocação
Connection pooling com RDS Pool gerenciado pela própria aplicação Express (pg-pool) Exige RDS Proxy (custo adicional ~$10–15/mês)
